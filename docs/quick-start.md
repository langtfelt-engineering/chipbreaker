# Quick start — a working integration in an afternoon

For a senior engineer with a C++ codebase who has been asked to evaluate this
and report back. It assumes nothing is installed except a compiler and `git`.

Three paths. Pick one; they do not depend on each other.

- [C or C++](#c-or-c) — the integration surface
- [Python](#python) — the fastest way to see a report
- [Command line](#command-line) — no build at all

Timings below are what it actually took on a clean machine, measured, not
estimated. If yours differ wildly, the [troubleshooting](#troubleshooting)
section probably has it.

---

## Before anything

You need **Rust 1.96 or later**. Nothing else is required by the engine itself.

```sh
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh    # or rustup.rs on Windows
git clone https://github.com/langtfelt-engineering/chipbreaker
cd chipbreaker
```

Confirm the toolchain and prove the build is sound in one step:

```sh
cargo run --release --bin chipbreaker -- selftest
```

Expect roughly **90 seconds** for the first build, then:

```
17 suites, 27054 cases, 0 failures
results hash: 1ccc6660b31f67ad5092a0248a89fc1c38cf1b9c2cf1fe5e4c022803f689c038
PASS
```

**That hash is the same on Linux, macOS, Windows and both WebAssembly targets.**
If yours matches, your build computes the same answers as ours. If it does not,
stop and tell us — that is a more interesting result than anything else on this
page.

## C or C++

*Measured: 19 s for the library, CMake configure and the example build, on a
warm cargo cache. Budget a few minutes on a cold one.*

### 1. Build the library

```sh
cargo build --release -p chipbreaker-abi
```

Produces `target/release/libchipbreaker.so` (`.dylib` on macOS,
`chipbreaker.dll` + `chipbreaker.dll.lib` on Windows). The header is committed
at `include/chipbreaker.h` — it is generated by `cbindgen` and checked in CI, so
it cannot drift from the library.

### 2. Build and run the reference host

```sh
cmake -S examples/c -B target/example-c -DCHIPBREAKER_ROOT=.
cmake --build target/example-c
```

Then run it against the evaluation corpus. On Windows the binary lands in a
per-configuration subdirectory, so it is `target/example-c/Release/host.exe`
there and `target/example-c/host` everywhere else:

```sh
./target/example-c/host \
    tests/corpus/eval/faced-gouge.nc \
    tests/corpus/tool/standard-library.json \
    tests/corpus/eval/stock.stl \
    tests/corpus/eval/nominal-faced.stl
```

```
chipbreaker 0.1.1, ABI 1
engine self-test 1ccc6660b31f67ad5092a0248a89fc1c38cf1b9c2cf1fe5e4c022803f689c038

DID NOT PASS -- read verdict.gates for which gate and why
report is 3592 bytes of chipbreaker.verification-report
```

Exit code 1: the gouge gate failed. That is the program being wrong, not the
run being wrong.

Set `CHIPBREAKER_WRITE_REPORT=out.json` to keep the document.

### 3. Read `examples/c/host.cpp`

It is 170 lines and it is the file to copy. Three things in it will save you the
most time:

**`CB_STATUS_REFUSED` is a success.** The engine declines jobs it cannot answer
for, and the sentence in `cb_result_message()` is the answer. Show it and stop.
Do not log it as an error and do not retry — nothing about the input has
changed. Try it:

```sh
./target/example-c/host tests/corpus/eval/g41.nc \
    tests/corpus/tool/standard-library.json tests/corpus/eval/stock.stl
```

```
REFUSED
line 4, column 1: G41 cutter radius compensation is not supported. The control,
not the program, decides the offset path, including lead-in and corner geometry
that differs between controls; simulating the uncompensated path would be wrong
by the tool radius everywhere. Post-process with compensation applied and G40
active
```

**An unchecked gate does not pass.** Omitting the nominal does not tell you the
part is good; it tells you the gouge gate never ran, and
`cb_result_pass()` returns 0. This is deliberate. A tool that reported success
for a check it did not perform would be worse than useless.

**One ownership rule.** The library allocates, you free with the matching
`_free`. Strings from getters belong to their handle and die with it.

### 4. Prove your integration is correct

`tests/corpus/eval/expectations.json` lists five jobs and what each must
produce — gate states, finding counts, and the depth of an error injected at a
known place. An integration that reproduces all five has handled the refusal
path, the unchecked-gate rule and the attribution, which are the three things
that get integrations wrong.

## Python

*Measured: 19 s for `maturin build --release` on a warm cache, then 2 s to run
the example.*

```sh
pip install maturin
cd crates/chipbreaker-python
maturin develop --release
```

```python
import chipbreaker

report = chipbreaker.verify(
    program="tests/corpus/eval/faced-gouge.nc",
    tools="tests/corpus/tool/standard-library.json",
    stock="tests/corpus/eval/stock.stl",
    nominal="tests/corpus/eval/nominal-faced.stl",
    resolution_mm=0.5,
)

print(report["verdict"]["pass"])                       # False
print(report["verdict"]["gates"]["gouge"])
# {'state': 'fail', 'why': '1 gouge above tolerance'}

for f in report["findings"]:
    lines = [s["line"] for s in f["attribution"]["segments"]]
    print(f["class"], round(f["severity"]["worst_depth_mm"], 3), "mm at lines", lines)
# gouge 1.0 mm at lines [27]
```

A refusal raises, and the message is the engine's sentence:

```python
try:
    chipbreaker.verify(program="tests/corpus/eval/siemens.mpf", tools=..., stock=...)
except chipbreaker.Refused as exc:
    print(exc)
# line 5: this looks like Siemens 840D, which is a different language rather
# than a dialect of RS-274 (found "DEF REAL")
```

## Command line

*Measured: under a minute after the build.*

```sh
cargo run --release --bin chipbreaker -- --help
```

`--json` on any verb emits a report schema. Exit codes are stable and are what a
build gate should read: **0** clear, **1** did not pass, **2** refused or
misused.

## Troubleshooting

**`cmake` says the library does not exist.** Run `cargo build --release -p
chipbreaker-abi` first. CMake names the file it wanted and the command that
produces it.

**Linux: `error while loading shared libraries: libchipbreaker.so`.** The CMake
build sets an rpath so the example runs from anywhere. If you are linking it
yourself, either set `LD_LIBRARY_PATH` to `target/release` or pass
`-Wl,-rpath,$PWD/target/release`.

**`error while loading shared libraries: chipbreaker.dll`.** You built the host
without CMake. The CMake build copies the DLL beside the executable on Windows
and sets an rpath elsewhere; a hand-rolled `cl` or `g++` line does neither.

**`maturin develop` cannot find a Python interpreter.** Activate a virtual
environment first. `maturin` installs into the active environment and refuses to
guess which one you meant.

**The self-test hash does not match.** Please tell us, with your platform and
`rustc --version`. This is the claim the whole engine rests on and a mismatch is
a serious result, not a configuration problem to work around.

**A job is refused for memory.** The message names a resolution that would fit.
That is not a workaround, it is the answer: the field scales as the square of
the inverse spacing, and the engine would rather refuse before allocating than
die halfway through.

**"the program's first motion uses tool number 0".** Your program has no `T`
word before its first move. Either add one or pass the tool explicitly —
`--tool` on the CLI, `cb_job_set_tool_id` in C, `tool=` in Python.
