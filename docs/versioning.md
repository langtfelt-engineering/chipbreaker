# Versioning and stability

Chipbreaker publishes **four things that can change**, and they change for
different reasons. Tying them to one number would make every release look like a
break in all four, which is the fastest way to teach an integrator to ignore
version numbers entirely.

| What | Where the number lives | Current |
|---|---|---|
| The crates | `Cargo.toml`, `cb_engine_version()` | `0.1.1` |
| The C ABI | `cb_abi_version()` | `1` |
| The verification report | `schema_version` in the document | `3` |
| The refusal document | `schema_version` in the document | `1` |
| The job file | `version` in the file | `1` |

Each section below says what a change to that number permits and what it
forbids.

---

## 1. What "stable" means before 1.0

Honestly: **the crate version is 0.x, and 0.x means the Rust API can change in a
minor release.** That is Cargo's convention and this project follows it rather
than inventing a private meaning for it.

What that does **not** mean is that everything is unsettled. The three things an
integrator builds against — the C ABI, the report schema, the CLI — have their
own numbers and their own rules, stated below, and those rules are in force now.
A pre-1.0 crate version reflects that the *Rust* surface is still being shaped
by units that have not been written yet; it is not a licence to move the report
schema without saying so.

If you are integrating today, build against the C ABI or the report schema.
Those are the surfaces with promises attached.

**Reaching 1.0** requires: the C ABI unchanged across two consecutive minor
releases with real integrations against it, the 5-axis work landed or explicitly
scoped out, and no known break pending in the report schema. It is not a date.

---

## 2. The C ABI — `cb_abi_version()`

Returns an integer. A host should read it at load time and refuse to continue if
it does not recognise the answer.

**A bump means an existing declaration changed meaning or disappeared:**

- a function removed or renamed
- a parameter added, removed, or reordered
- a parameter's or return value's type changed
- an existing enumerator's numeric value changed
- a struct's layout altered

**These are not bumps, and a caller compiled against an older header keeps
working:**

- a new function added
- a new enumerator appended to `cb_status` — which is why callers must treat an
  unrecognised status as "something newer than me" rather than as garbage, and
  why `CB_STATUS_OK` and `CB_STATUS_REFUSED` are pinned at 0 and 1 forever
- documentation changes
- behaviour changes that do not alter a declaration, such as a new refusal
  reason or a faster algorithm

The header is generated by `cbindgen` from the Rust source, committed to the
repository, and **checked in CI**. A header that has drifted from the library it
describes is worse than no header: it compiles, and then the two disagree at run
time.

### What is deliberately *not* promised

Refusal *messages* are not stable text. They are written for people, they get
better, and a caller that pattern-matches on their wording has built on sand.
Match on `CB_STATUS_REFUSED`; show the message.

---

## 3. The report schemas

`chipbreaker.verification-report` and `chipbreaker.refusal` carry their own
`schema` and `schema_version`, and are versioned **independently of each other
and of the crate**. They describe different things and would otherwise force a
break in one to look like a break in the other.

**A major bump — the only kind there is** — means an existing field changed
meaning or was removed. There have been two:

| Version | Change | Why it was worth breaking |
|---|---|---|
| 2 | `accepted` removed in favour of `verdict.gates` | `accepted` meant "no gouge above tolerance", and a consumer reading the obvious field would have passed a program that drives a holder into a fixture |
| 3 | `penetration_mm` → `overlap_along_ray_mm`, `clearance_mm` → `clearance_along_ray_mm`, `area_mm2`/`volume_mm3` → `*_estimate_*` | each name promised more than the value delivered, and a name travels into a consumer's codebase where the accompanying note does not |

**Adding a field does not bump the version.** A consumer that ignores unknown
keys is unaffected, and one that does not was going to break on anything. The
most recent addition is `numerical_semantics.comparison`, which reports whether
a nominal was supplied at all: when one was, the five comparison figures sit
exactly where they always have and every existing report is byte-for-byte
unchanged.

**A field is removed and replaced, never aliased.** A consumer reading a
retired name finds nothing and fails, at the moment it can still be fixed,
rather than silently reading something that is no longer what it thinks.

### Relation to the crate version

None, deliberately. A patch release of the crate may add a report field. A major
release of the crate may leave the schema untouched. The schema's own number is
the only one that describes the schema.

What *is* guaranteed: a report always states its own `schema` and
`schema_version`, so a document is self-describing without reference to which
build produced it.

---

## 4. The CLI

`chipbreaker <verb>` is covered by the crate version, with 0.x rules.

Within that:

- **Exit codes are stable.** `0` clear, `1` did not pass, `2` refused or
  misused. A build gate depends on these and they are cheap to keep.
- **`--json` output is a report schema**, and follows the schema rules above
  rather than the crate rules.
- **Human-readable output is not an interface.** It is formatted for a person
  and will change. Parse `--json`.

---

## 5. The job file

`schema: chipbreaker.job`, `version: 1`. Same rules as the report schemas: a new
optional key is an addition, a changed meaning is a bump.

---

## 6. Pinned dependencies

Four dependencies are pinned with `=` because their output feeds a canonical
hash that is a published guarantee: `robust`, `blake3`, `rand`, and
`serde_json`'s float handling. A patch release of any of them could change a
digest that customers have recorded beside their reports.

Bumping one is a deliberate act with its own procedure — see `CONTRIBUTING.md`,
"Changing a pinned dependency". It is not something a dependency-update bot may
do, and CI enforces the pins.

---

## 7. The self-test digest

Not a version, but it behaves like one and integrators use it as such.

The digest identifies the **build's behaviour**: it is identical on Linux,
macOS, Windows, `wasm32-wasip1` and `wasm32-unknown-unknown`, so two builds
sharing a digest will produce the same answers for the same inputs.

It moves when a computed answer moves, and **not** when performance, formatting,
documentation or scheduling changes. A digest change in a release is called out
in the changelog with what moved and why; a digest change that nobody can
explain is a defect, not a release note.
